# 键览 KeyGlance

双击 ⌘，立刻把**当前前台 App 的全部菜单快捷键**铺在屏幕上 —— macOS 26（Tahoe）原生 + Liquid Glass 面板。

参考产品：FlyKey（键指如飞）。这是一个从零写的原生实现，不是套壳。

## 它现在能做什么

- **双击修饰键唤出**：默认双击 ⌘，可在设置里换成 ⌃ / ⌥ / ⇧，或彻底关闭双击触发。
- **读取真实菜单**：通过 Accessibility 读前台 App 的菜单栏，所以显示的快捷键和菜单里完全一致（含 ⌘⇧⌥⌃ 组合、⌫ ↩ ⇥ ⎋ ↑↓ 等符号键、F1–F12）。
- **一屏铺开的清单**（学「键指如飞」的排法）：菜单名当行内的小节标题，条目在等宽的列里自上往下流，一列满了就开下一列；**快捷键在左、标题在右**，一组键帽右对齐到统一的栏宽，于是整列标题排成一条直线。一个菜单长到跨列时，续列顶上再写一次菜单名。
- **靠长高而不是靠压缩**：面板从最矮（240）开始长，越长每列能放的条目越多、需要的列越少，取「刚好放得进屏宽」的那个高度（上限 = 屏高 − 80）；行高依次试 26 / 24 / 22，优先用最舒展的。条目多到满高、最紧行高都放不下时才允许横向滚动 —— 任何情况下都**不裁切、不压缩标题**。
- **一个分区一个色块**：每个菜单是一块 8pt 圆角、2pt 间隙的浅色底，菜单名用同色的半粗字。块内各行画同一颜色、只有首尾行露圆角，所以跨列续排时看着还是一整块。
- **颜色按类目**名字**分配，不按行号**（2026-10-30 改）：以前是 `hues[section % 10]`——同一个菜单在不同的 App 里位置不同、颜色就不同，扫一眼认不出是"文件"还是"编辑"。现在 `PanelPalette.resolveHues(for:)` 按**菜单名**解析：常见名字（常用 / 文件 / 编辑 / 显示 / 窗口 / 帮助 / 视图 / 工具 / 格式 / 插入 / 图像 / 系统，中英文都收录）走固定色相表，**同一个菜单名在任何 App 里都是同一个颜色**；没收录的名字用自己的 FNV-1a 哈希取色——**不能用 Swift 的 `hashValue`**，它每次进程启动都不同，同一个菜单两次启动会拿到不同颜色。同一屏里如果两个类目撞了色，后者往后挪一个空位（顺序固定，所以同一个 App 每次打开结果一样），而固定表里的类目颜色**不会被别人挤掉**。
- **色块是真的液态玻璃**（2026-10-30 改）：以前是自己在单元格里画一块半透明色；现在每块菜单用一块真的 `NSGlassEffectView`（`style = .regular`，颜色交给 `tintColor`，圆角/边缘高光/明暗全由系统自己画，将来 macOS 改玻璃效果这里自动跟上）。**一个菜单一块，不是一行一块**：一行一块会露出接缝，而且十几行就是十几个玻璃视图，背景采样太贵。
- **玻璃层必须挂在表格里，而且自己也要 flipped**（2026-10-30 改，踩过两个坑）：① 玻璃层挂在滚动视图的**裁剪视图**里时，行矩形（表格坐标）和玻璃视图（裁剪视图坐标）是两套坐标系，`convert` 会在中间把 y 镜像掉，块整个上下颠倒、跟文字对不上——所以改成直接挂进**表格**里，一套坐标从头用到尾。② 但 `BlockGlassLayer` 默认 `isFlipped == false`，而表格是 flipped 的，层内 y 方向跟表格相反，块照样错位——**这一层必须 `override var isFlipped: Bool { true }`**。玻璃层是背景，还要 `override func hitTest` 返回 nil，别挡鼠标。
- **玻璃的材质会往外溢一点**：`NSGlassEffectView` 的内部材质层比 bounds 大一圈（边缘折射要留余量），`masksToBounds = true` 会让玻璃整个不渲染（这条路堵死）。所以色块边界**不要靠量渲染出来的像素**判断，要按 frame 算。
- **色块着色要淡**：玻璃材质本身就有不透明度，`tintColor` 一浓就变成实色方块、背后的壁纸透不过来，玻璃感反而没了。实测深色 0.08 / 浅色 0.06 比较稳；`KEYGLANCE_BLOCK_TINT` 可以现场扫。
- **跨列不重复菜单名**：一个菜单长到跨列时，续列顶上**不再写一遍菜单名**——颜色是按类目名字定的，同一类目在两列里是同一个颜色，靠颜色就能认出是同一类目，再写一遍名字反而啰嗦。（中间试过"续列重复标题"，用户明确否掉了。）
- **但标题不能单独留在列尾**：标题后面至少要跟得上一行条目，否则那列末尾只有一行孤零零的标题色块。
- **顶栏统一高度 + 系统玻璃**（2026-10-30 改）：软件名框原来靠文字自己撑高（26.5pt）、搜索框写死 25pt，差 2pt，顶边底边各错 1pt，一眼就能看出不在一条线上。现在三者都用 `PanelMetrics.controlHeight`（26pt）：软件名框、**中间那行提示（条数 · 双击切换 · esc 关闭）**、搜索框。提示那行原先是纯文字浮在 overlay 上，看着跟左右两块不是一个体系，现在也装进玻璃药丸——**一行三种高度太杂**。玻璃交给 SwiftUI：软件名和提示是 `.glassEffect(.regular, in:)` 的静态玻璃；搜索框是 `.glassEffect(.regular.interactive(), ...)`——**交互玻璃是 macOS 27 才有的**（AppKit 侧对应 `NSGlassEffectView.effectIsInteractive`），能让动的控件才有反馈（提示文字不可点，用静态玻璃）。整排玻璃再套一层 `GlassEffectContainer`，让系统统一处理。
- **顶栏只有两样**：左边软件名（15pt 半粗，装在一个圆角框里），右边搜索框；没有图标、没有条数、没有分隔线，底部也没有提示条。
- **尺寸贴合内容**：列宽 = 最长的一行（键帽栏 + 标题 + 内距），夹在 148–300 之间；面板宽 = 列数 × 列宽 + 列间距（10pt），上限 = 屏宽 − 60；末列留 14pt 给滚动条，键帽不会被遮挡。
- **「常用」分区**：统计你在这个 App 里最常按的组合键，排成第一列（只按次数计数，不记录任何文字）。
- **「系统」分区**：读取 `com.apple.symbolichotkeys`，显示调度中心、应用窗口、聚焦、强制退出、截屏等系统级快捷键，并跟随你在系统设置里的改动。
- **搜索**：打开即聚焦搜索框，输入即筛选（中英文、快捷键符号都能匹配）。
- **原生交互**：`esc` 关闭、面板外点一下关闭、再双击一次关闭；关闭后焦点回到原来的 App。
- **Liquid Glass**：面板用 `NSGlassEffectView`（macOS 26 的系统玻璃材质），边框、圆角、明暗全部交给 Apple 自己画，没有自绘描边。
- **明暗跟系统**：玻璃底色用 `NSGlassEffectView.tintColor`（不再手叠色块），并监听系统主题切换实时重算；面板开着时切换明暗也会立刻跟着变。
- **内容贴边**：窗口是隐藏标题栏的 `.titled` 窗口，`NSHostingView.safeAreaRegions = []` 去掉系统预留的标题栏安全区，否则面板顶部会空出一条。
- **图标日/夜两套**：用 Icon Composer 的 `.icon` 包（`Tools/makeicon.swift` 生成，`actool` 编译成 `Assets.car`）。浅色＝白底黑 ⌘，深色＝黑底白 ⌘，跟随系统自动切换。
- **窗口形状也是系统的**：面板窗口是 `.titled + .fullSizeContentView`（标题栏透明、红绿灯隐藏），不是 `.borderless`。borderless 窗口的阴影按矩形计算，圆角处会露出直角的黑影；带标题栏的窗口由系统直接给出圆角与圆角阴影。
- **进场动画**：玻璃底板先隐形上屏（约 80ms，让玻璃采样好背景、首屏单元格就位），内容再用 AppKit 对 hosting view 的透明度淡入 0.16s；收起时 0.09s 淡出再移除窗口。淡入这 160ms 里主线程**只服务合成器**：不排版、不换内容、不改窗口尺寸。冷启动等内容读完排好版才淡入（最多等 0.3s）；命中缓存就先用上次的内容淡入，真有变化的内容等淡完 0.15s 再换。
- **台前调度（Stage Manager）里也居中**：系统不会把窗口摆到"舞台区"的中心，它只是把窗口**夹**回允许的范围里——左边越过缩略栏就顶回来，右边越过屏幕边就拉回来。关键在于**夹取只发生在窗口上屏的那一刻**：窗口已经在屏上了，再挪它系统就不管了（实测放好 2 秒不动、缩略栏展开时也不动）。所以面板的顺序是"**先上屏（透明的），再摆到整屏真正的正中**"，水平中心取整屏的 `frame.midX`（不是"舞台区"的中心）。放好之后位置就不再被系统碰。
- **不再反推"舞台几何"**（2026-10-29 改）：旧版是"看窗口被挪到哪，再反推舞台中心和宽度"（舞台宽 = 2×(屏右边缘 − 挪完的中线)），把结果按屏幕尺寸存进 `stageWidthLimitsByScreen` / `stageCenterOffsetsByScreen`。那个公式只在一种巧合下成立（窗口右边缘刚好被夹到屏幕右边），其余情况推出来的是错的；而且存下来的值会过期——系统改一次缩略栏宽度就失效，面板会长期偏在一侧（实测缓存值是"中心 833.5 / 宽上限 1341"，真实可用区是"中心 866.5 / 宽 1291"，面板被顶到 x=221 贴着缩略栏、右边空出 66pt）。现在每次打开都按整屏正中摆，旧缓存已清掉。
- **想知道系统让出多少**：`NSWindow.constrainFrameRect(_:to:)` 把一个跑到屏幕外的矩形夹回来，夹住的位置就是边界（实测左边界在 61…221 之间，会随缩略栏状态变）。这个值只用来打日志做体检，不参与摆放——摆还是按整屏正中摆。
- **搜索时不改面板高度**：面板在打开时按完整清单击一次高度，之后在搜索框里打字 / 删字 / 回车确认都**不**再改窗口尺寸。原因见下面「内容错位的真凶」——一边过滤一边改窗口高度，玻璃或内容视图总有一帧对不上，看起来就是"内容往上窜、只剩下面一截"。代价是搜出两三条时下半部分是空玻璃。
- **横向完全锁死**：面板的表格从不启用横向滚动条（`hasHorizontalScroller = false`、弹性为 `.none`），表格宽度恒等于可视宽，并在滚动通知里把 `origin.x` 钉回 0，触控板横滑也推不动。
- **不会横向晃动**：内容装得下时表格宽度锁死等于可视区（`hasHorizontalScroller = false`、`horizontalScrollElasticity = .none`），只有列多到放不下才允许左右滚。
- **滚动条只在滚动时出现**：面板和设置页的滚动视图都强制 `scrollerStyle = .overlay` + `autohidesScrollers`，即便系统偏好是「始终显示」（接了鼠标时就是这种），也不会常驻一条。
- **不闪**：打开/关闭都不对窗口做透明度动画（partial alpha 的玻璃会透出亮底，看着像闪白），窗口带着内容一次性出现、收起时直接消失；冷启动时内容用 0.15s 淡入。明暗和玻璃底色取自系统偏好，避免首帧用了浅色 tint。
- **内容只在打开前定稿**：切到某个 App 后 0.6s 在后台把它的快捷键读进缓存（`prefetch`）；双击 ⌘ 时直接铺这份"已排好版"的内容。打开时若发现菜单又变了，只更新缓存、不当场重排——否则用户看到的是"出来以后文字又自己变了一次"。缓存 2s 内视为新鲜，重复打开同一个 App 内容稳定。
- **开得快**：常用 App 第二次起 ~12ms 出面板；首次也有内容缓存 + 预建窗口，见下面「性能」。
- **菜单栏常驻**：**左键单击图标开/关面板**（再点一次收起），**右键（或 ⌃ 单击）出菜单**：关于 / 设置 / 退出。触发方式、权限等其余设置都在设置面板里。
- **设置窗口（单页）**：没有侧边栏，通用 / 权限 / 更新 / 关于 依次排在一页里滚动；触发方式、双击间隔（0.20–0.60 秒）、显示搜索框、显示菜单栏图标、面板动画、登录时启动；「常用」分区 / 系统快捷键 / 使用记录三个开关和清除按钮。
- **设置界面里的「按住试试」提示**（2026-10-30 加，同日撤销）：本来给双击手势做了个实时提示胶囊，
  用户澄清是要**新增一种触发方式**（按住显示/松开隐藏），不是提示胶囊，已全部撤掉。
  监测器改名为 `ModifierTriggerMonitor`（文件 `Sources/ModifierTriggerMonitor.swift`），
  同时负责双击和按住两种手势。
- **触发方式是一个下拉，修饰键 × 手势合成一个选项**（2026-10-30 改）：`TriggerMode` 枚举有 9 项
  （双击 ⌘/⌃/⌥/⇧、按住 ⌘/⌃/⌥/⇧、关闭）。设置里**一行**「触发方式」+ 一个下拉，
  右边一句话说明怎么用（"按住 ⌘ 显示，松开隐藏"）。选「按住」时「双击间隔」那一行**整行消失**（双击才用得上）。
  - 存储：新键 `triggerMode`（合成值）；老版本存的是分开的 `triggerKey` + `triggerGesture`，
    `loadTriggerMode` 启动时合并一次并写回。
  - **迁移的坑**：判断"用户设过没有"必须查 `persistentDomain(forName:)`，
    **不能**用 `object(forKey:)` 或 `string(forKey:)`——`register(defaults:)` 注册的默认值
    会让这两个都返回非 nil，判不出注册值和真值，迁移直接失效（表现：老设置被重置成默认）。
    同理老的两个键**不能**注册默认值。
- **按住模式必须只按着触发键本身**（2026-10-30 改）：⌘⇧ 这种组合**不算**——
  那是在用带修饰键的快捷键（比如 ⇧⌘4 截屏），不是想看这张表。
  判据是"除它之外没有别的修饰键"（`flags` 减去触发键和 capsLock 等无关标志后为空），
  所以叠加一个修饰键时面板会**立刻收起**。实测：单独 ⌘ 显示、只按 ⇧/⌥ 不显示、⌘+⇧ / ⌘+⌃ 都不显示。
- **按住模式下绝对不能抢焦点**（2026-10-30 改，关键约束）：用户是一边按着 ⌘ 一边在别的 App 里操作，面板要是抢了焦点，⌘C 就跑到面板的搜索框里去了，目标 App 收不到。所以按住模式：
  - `present()` 里**不调** `NSApp.activate`（这一句是关键）；
  - `hide()` 里**不**把焦点还给上一个 App（`heldMode` 分支直接 `orderOut`）；
  - 面板打开时**不装**「点外面就关」和「别的 App 激活就关」这两个监视器——面板跟着修饰键走，松开才收。
  - 实测按住期间前台 App 始终不变（焦点一点没动）。
- **按住模式必须用 `makeKeyAndOrderFront`，不能用 `orderFront`**（2026-10-30 改，踩过的坑）：
  面板是 `.nonactivatingPanel`，拿 key 状态**不会激活键览**（前台 App 照旧 active），
  但 `NSGlassEffectView` **需要 key 状态才能采样到背景**——用 `orderFront` 的话材质整个不渲染，
  面板变成一块死黑，**类目色块的颜色也全丢了**（截图对比才看出来）。
  → 所以「不抢焦点」靠的是 `.nonactivatingPanel` + 不调 `NSApp.activate`，
  **不是**靠不用 `makeKeyAndOrderFront`。两件事要分开想。
- **按住模式下搜索框保留但点不动**（2026-10-30 改）：顶栏三个控件（软件名 / 提示 / 搜索框）
  外观跟双击模式完全一致，搜索框不隐藏（藏了看着像"功能丢了"）。因为键盘还在前台 App 那边，
  按住时搜索框用不了，所以把它**画成不可用的样子**（`opacity 0.72` + 去掉交互玻璃 + `allowsHitTesting(false)`，
  鼠标悬停有说明），而不是摆一个点下去没反应的框。
  同理 `onAppear` 里按住模式**不自动聚焦**搜索框（聚也聚不上）。
  提示文字改成「松开 ⌘ 隐藏」。
- **按住模式的两个边界**（都处理了）：
  - 快速点一下（0.05 秒就松手，菜单还没读完）：`hideHeld()` 里把 `loadToken` 加一作废这次加载，否则面板会在修饰键早就不在了之后自己冒出来。
  - 按住期间切到别的 App：`workspaceAppActivated` 里发现修饰键还按着，就 `showHeld(for: 新App)` 换内容，不然摊开的是上一个 App 的快捷键。
- **设置窗口开着的时候双击不弹面板**（2026-10-30 改）：用户是在设置界面里**试手势**，不是要唤出面板。
  `handleTrigger` 里先看 `settingsWindow?.window?.isKeyWindow` —— 是设置窗口就只让提示亮一下，直接返回。
  正常场景（不在设置窗口）双击照旧开/关面板。
- **更新在设置里**：显示当前版本，按钮手动检查 GitHub 上的 latest release（显示「已是最新」或「有新版本 x.y.z」），可以看发布说明，也可以一键「下载并安装」；「自动检查更新」默认开（启动时及每 24 小时最多一次），「自动下载并安装」默认关。菜单栏右键菜单里也有「检查更新…」，有新版本时标题会变成「有新版本 x.y.z…」。
- **首次引导**：申请辅助功能权限的欢迎窗口，带"已授权，重新检测"。

## 签名与辅助功能授权

临时签名（ad-hoc）的 App，macOS 的「指定要求」是 **cdhash**——每编译一次就换一个，于是系统把新版当成另一个 App：辅助功能列表里的旧开关看着是开的却不生效，用户得删掉再加一次。自更新装完也一样。

所以 `build.sh` 现在用一张固定的自签名证书签（证书名 `KeyGlance Self-Signed`，在登录钥匙串里，备份在 `~/Library/Application Support/KeyGlance/signing/`）：

```
designated => identifier "com.hushixiong.KeyGlance" and certificate root = H"1409c8f0…"
```

只要证书不变，这个要求就不变——重新编译、自更新、换版本号都不影响，授权一次以后一直有效。找不到证书时脚本才退回 ad-hoc（那时又要重新授权，会在编译日志里提示）。想换签名人：`KEYGLANCE_SIGN_ID="证书名" ./build.sh`。

## 更新（自更新）

版本信息只认 GitHub：`GET https://api.github.com/repos/liaooabc/KeyGlance/releases/latest`，tag 是版本号（去掉 v），附件优先取 `.zip`（将来换 `.dmg` 也能装）。比较版本号按点分段整数比，所以 1.10 > 1.9。

装新版的流程（Sparkle 那套的精简版，代码在 `Sources/Updater.swift`）：

1. 下载附件到临时目录（`URLSessionDownloadTask` 带进度，小于 100 KB 直接判定不对）。
2. 解包（`ditto -x -k`，dmg 则 `hdiutil attach`），在解出来的目录里找 `.app`。
3. **验包**：`CFBundleIdentifier` 必须等于自己的 bundle id，`CFBundleShortVersionString` 不能低于发布版本，否则中止。
4. 拷到 `~/Library/Application Support/KeyGlance/Update/新版.app` 暂存。
5. 写一个 shell 脚本并启动它，然后本进程退出；脚本等进程消失后「备份旧包 → `ditto` 放新包 → 去掉 quarantine → 重新打开」，任何一步失败都把旧包放回去再打开。

几个刻意这么做的点：

- **不覆盖正在运行的包**：运行中的 App 被换掉最容易留下半新半旧、一开就崩的包，所以替换一定发生在退出之后。
- **先检查写权限**：`/Applications` 不可写、或 App 是从 DMG/压缩包里直接运行（路径里有 `AppTranslocation`）时，在退出前就报错，不会出现「App 没了也没装上」。
- **失败一律弹系统警告框说清楚原因**（权限、磁盘、网络都可能挡），不静默失败。

调试用：`KEYGLANCE_FAKE_VERSION=0.9.0` 假装本机是旧版，可以直接看「有新版本」那一行并走完下载安装（会替换并重启真正运行的那个 App，建议先从副本目录启动再试）。

## 性能（实测，1512×982 屏）

| 场景 | 耗时 |
| --- | --- |
| 首次打开某 App（以访达 107 条为例） | 面板 90ms 出现，首行在其后 ~58ms 绘制 |
| 同一 App 再打开 | ~20ms（内容、列、单元格都复用，窗口尺寸不变） |
| 滚动 | 只绘制可见单元格（NSTableView 虚拟化），不再整棵树重排 |
| AX 菜单读取 | 139ms → 55ms（一次性多属性取值，1 次 IPC/条） |
| 入场淡入（1373×768、121 条） | 0 掉帧，帧间隔 8.3ms（120Hz） |

做法：`AXUIElementCopyMultipleAttributeValues` 批读、按 App 缓存解析结果、启动时预建面板与玻璃视图、先按最终尺寸铺面板再填内容（不再有"先小后大"的窗口跳变）、`NSHostingView.sizingOptions = []` 防止 SwiftUI 反过来改窗口尺寸。

**内容错位的真凶（2026-10-29 查了很久，别再引回来）**：`NSGlassEffectView` 会照自己内容报"理想高度"，面板改高度时它会自己涨成 700/990 这种数，把 `contentView` 一起撑大（日志里出现 `window h=601 container=991`），于是内容被裁掉上半截、只露下面一截。让 `NSHostingView.intrinsicContentSize` 返回 `noIntrinsicMetric`、再外挂一层"把 bounds 抄给子视图"的容器，都压不住。最终做法：搜索期间根本不改窗口高度。

复现真实输入的小工具（面板是非激活面板，脚本打的字进不去，要用真实键盘事件）：`Tools/clicker.swift`、`Tools/typer.swift`、`Tools/keyer.swift`——先用 CGEvent 点面板和搜索框拿焦点，再发键码（a=0、Return=36、Delete=51）。排查靠 `KEYGLANCE_DEBUG=1` 打的 `geom` 行（window/container/glass/host 四层高度）和 `key keyCode=… responder=…` 行。

**掉帧的三个真实来源**（都已修，别再引回来）：

1. 窗口高度有两套算法：`PanelColumns` 算 `chrome + 12 + 最高列`，而表格回报的行高走 `header + 上下留白 + 行数×行高`，两者差 2pt。于是每次打开都会 `setFrame(display:true)` + `invalidateShadow()` 来回抖两次，单次 40ms，正好落在淡入里。现在只有一处算法（`chrome + verticalPadding + tallest`）。
2. 冷启动时"先上屏、后填内容"：整表重画（90 行约 40ms，121 行更多）落在淡入中。现在内容落地后才开始淡入。
3. 面板开着时内容变了（Safari 这类菜单跟着页面走）：整表重建约 100ms。现在淡入期间一律推迟，淡完再换。

量法：`KEYGLANCE_DEBUG=1 KEYGLANCE_DEMO_REPEAT=5 ./build/KeyGlance.app/Contents/MacOS/KeyGlance` 会自动开合 5 次面板，日志里 `hitch:` 行是超过 24ms 的帧，`reveal start/end` 是淡入区间——**淡入区间内不该出现 hitch**，`geometry panel=… | allowed x=…` 那行是这次的摆放基准。

## 已知边界

- 「常用」只统计带 ⌘/⌃/⌥ 的组合，且只存"次数"，不存文字；可在设置里关掉并一键清除。
- 系统快捷键表来自固定 ID 映射，个别非常冷门的项若被系统改名可能对不上；用户自己改过的绑定会以 plist 里的值为准。
- 只显示走 **菜单栏** 的快捷键。没有菜单项的快捷键（如 App 自定义的全局热键、终端里的快捷键）读不到——这一点和 FlyKey 一样。
- 有些 App（游戏、部分 Electron/Unity 自绘界面）不暴露 AX 菜单，会显示"没有可显示的快捷键"。
- 与 FlyKey 同时运行会抢同一个双击 ⌘；把其中一个改成 ⌃ 或 ⌥ 即可。
- 图标目前是单套（深色下系统会自动压暗）；想要真正的日/夜/着色三套图标需要改用 Asset Catalog + `actool`（下一步可做）。
- 登录项用 `SMAppService`，ad-hoc 签名下若被系统拒绝，设置里会给出提示。

## 图标（App 图标怎么来的、多大合适）

图标不是手画的图，是 `Tools/makeicon.swift` 现场生成的 **Icon Composer 文档**：一张 1024×1024 的满幅底色 + 一个居中的 `command` 字形（白天白底黑字 / 暗夜黑底白字，靠 `icon.json` 里的 `opacity-specializations` 互斥切换），再由 `build.sh` 里的 `actool` 编成 `Assets.car` + `AppIcon.icns`。

- **字形大小只由一处决定**：`makeicon.swift` 里 `glyph(..., pointSize: 600, weight: .bold)` 的 `pointSize`。
- **改完必须删 `Resources/Assets.car`**：`build.sh` 只有在 `Assets.car` 不存在时才重新生成图标，不删的话改了也白改。

### 各档字形占画布的比例（实测）

量法：用对应 `pointSize` 生成 `.icon`，`ictool --export-image --rendition Default --width 512 --height 512` 渲染，再数深色像素的 bbox（`command` 字形是纯黑，阈值亮度 < 0.30）。「占画布」= bbox 边长 / 512，因为底色满幅，所以这个数也等于占 Finder 瓦片的比例。

| pointSize | 字形 bbox（512 渲染） | 占画布 / 占瓦片 |
| --- | --- | --- |
| 560（1.1.1 及以前发布版） | 264 px | 51.6% |
| 660（1.1.5 实际发布的图标） | 500 px / 1024 画布 | 60.7% |
| **600（1.1.6 起发布，当前）** | 456 px / 1024 画布 | **55.3%** |
| 670（试过，比 685 小一档） | 508 px / 1024 画布 | 61.7% |
| 685（1.1.3 / 1.1.4 发布的） | 322 px | 63.1% |
| 700（试过，偏大一档） | 330 px | 64.5% |
| 740 | 348 px | 68.0% |
| 780 | 368 px | 71.9% |

### 参照：为什么 51.6% 显得偏小

Finder 截图里三块图标瓦片都是 122 px：

| 图标 | 图形尺寸 | 占瓦片 |
| --- | --- | --- |
| 键览（560） | 62 px | 50.8% |
| 更新雷达（圆环外径） | 82 px | 67.2% |
| 苹果「股市」（满幅图形） | 118 px | 96.7%（类型不同，仅供参考） |

苹果自家"单符号"型图标（备忘录、指南针等）基本落在 60%–70%；键览 1.1.1 时的 51.6%，和更新雷达并排会明显"缩在中间"。**740 正好和更新雷达的圆环齐平（68.0% vs 67.6%），700 是 64.5%，685 是 63.1%，660 是 60.7%，现在定在 600 / 55.3%（理由见下面的「定档 600」）。** 笔画粗细不用另外调：放大是等比缩放，笔画/字宽 0.113 的比例不变。

对比图：`docs/键览图标-字号对比.png`（560 / 700 / 740 / 780 四档并排）。

### 定档 600（2026-10-30，家族设计对齐）

660 换上后，把「更新雷达」和「键览」并排截图（Finder 里各 120 px 瓦片）直接比，键览仍然显得大一号。实测两者占瓦片：

| 图标 | 字形 bbox / 瓦片 | 墨水覆盖率 | r80（占瓦片） |
| --- | --- | --- | --- |
| 更新雷达（圆环外径） | 67.7% | 20.1% | 35.6% |
| 键览 660（⌘） | 60.7% | 19.9% | 37.3% |

结论：**「占瓦片」这个尺子对 ⌘ 不公平**——⌘ 是一块方方正正、四角都顶出去的密字形，它的墨水覆盖率和圆环一样（20%），但外缘伸得比圆环远（r80 37.3% > 35.6%），所以看着更大。圆环有四角留白，`command` 没有。

按「外缘不许超出圆环」这条家族规则反解：r80 要从 37.3% 降到 35.6% 以下，pointSize 上限约 620；考虑到 ⌘ 的笔画密度，取 **600（占瓦片 55.3%，r80 ≈ 33.9%）**，让 ⌘ 明确地收在圆环轮廓里面。实测 /Applications 里渲染出来的位图：字形 456 px / 1024 画布 / 824 瓦片 = 55.3%，与预期一致。

以后判断「和更新雷达一样大」不要只看 bbox 占比，看 r80（墨水质量的半径分布）：圆环 35.6%，键览 600 是 33.9%，这才是两者并排看着同一家的位置。

对比图：`docs/键览图标-600-家族对比.png`（更新雷达 / 键览 660 旧 / 键览 600 新，都是 /Applications 里渲染的真图标）。

**随 1.1.6 发布（2026-10-30）**：tag v1.1.6，附件 KeyGlance-1.1.6-arm64.zip，sha256 b6e683d0…c954。

### 定档 660（2026-10-30）

选型走了四步：560（原发布版，51.6%）→ 740（用户说「太大了，不精致」）→ 700（说「再小一点点」）→ 685（换上又觉得还大一点点）→ **660**。
685 只降了 2.1%，看着还是偏大，所以这次一步降到位：**660 / 60.7%**，随 **1.1.5** 发布（2026-10-30）。还在苹果单符号图标的常见区间里；真要再小就往 640 走（≈58.9%），别再往回加。
上面的尺子是量 512 渲染里字形 bbox；Finder 瓦片里要换算：**图标位图里那块圆角瓦片只占 0.805**（1024 画布 → 824 的瓦片），
所以「字形/瓦片」= bbox/512 ÷ 0.805。

Finder 实测（`docs/键览图标-700-Finder实测.png`，截图直接从访达窗口抓，图标视图 64pt @2x）：

| 量的是什么 | 像素 | 占瓦片 |
| --- | --- | --- |
| 圆角瓦片（白底那块） | ≈103 px（位图 128 × 0.805） | 100% |
| ⌘ 字形 bbox | 66 px | **≈64%** |

和 512 渲染量到的 64.5% 一致（66/103 = 64.1%，量化误差 1px 内）。换档后照这个复核：瓦片 ≈103px 时字形 66px 左右就对。
2026-10-29 定 685 后再量一遍：512 渲染里字形 260px、白瓦片 412px ⇒ **63.1%**（预计 322.9px 换算到带内边距的那张图是 260px，吻合）。
2026-10-30 定 660 后量（1024 画布口径）：字形 500px、白瓦片 824px ⇒ **60.7%**；685 同口径是 520px / 824px = 63.1%。
